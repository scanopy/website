## Hosts

Hosts represent devices on your network. They are automatically discovered during network scans.

### Consolidating Duplicate Hosts

When a device appears on multiple VLANs or through different discovery methods, it may be discovered as separate hosts. Use consolidation to merge them:

1. Open the host you want to keep (primary)
2. Click **Consolidate**
3. Select the duplicate host(s) to merge
4. Confirm

The primary host gains all interfaces, services, and properties from the merged hosts. Use this to unify a server that has interfaces on multiple VLANs into a single logical host.

#### Restrictions

- Cannot consolidate a host with itself.
- Cannot consolidate a host that has a daemon - consolidate into it instead.

### Unclaimed Open Ports

Ports discovered without a matching service definition are assigned to an "Unclaimed Open Ports" placeholder. To reassign them:

1. Open the host and go to the **Services** tab
2. Select ports from "Unclaimed Open Ports"
3. Click **Transfer Ports** on the service you want to assign them to

Useful when Scanopy detects an open port but can't identify the service running on it.

### Network Identities

A host can present addresses and MACs on the network from its own interfaces, beyond its configured NICs. Common sources:

- macvlan shim interfaces on Docker hosts
- keepalived virtual IPs
- a service given its own LAN address
- network or SNMP simulators that answer as separate devices

Scanopy records each identity as its own host, linked to a "Network Identities" service on the host that presents it and to the interface it sits on. Like "Unclaimed Open Ports", this service is a placeholder, not a running service. It holds the link between the host and the addresses it presents.

Each identity host carries a **Network identity** tag and appears nested under the host that presents it in the [Workloads perspective](/using-scanopy/topology/workloads). Scanopy does not classify what an identity is. An emulated device, a virtual IP and a second address of the host all look the same from the host's interface list. The identity's own data, such as an SNMP sysName, shows what it presents itself as.

### Virtualization Relationships

Scanopy tracks which VMs and containers run on which hosts. These integrations record the relationships:

<VirtualizationRelationships />

You can also assign a host to any hypervisor or container runtime service by hand, from the host's Virtualization settings.

These relationships appear in the topology and host details, showing your virtualization hierarchy. The [Workloads perspective](/using-scanopy/topology/workloads) provides a dedicated view of this hierarchy.

The host list opens grouped by **Virtualized By**, which shows each hierarchy as a tree. Each group is named after the host at the top of a chain, such as a Proxmox node, and lists that host first with its guests under it. A guest that runs others, such as a VM running containers, heads a collapsible section of its own holding the VM and then its containers. A line down the left edge of each section joins the rows inside it. Hosts that neither run under nor run anything fall in **Not Virtualized**. The **Virtualized By** column and its filter still show the service a host runs under directly.

### Service Detection

Scanopy automatically detects 200+ services. See [Service Detection](/reference/service-detection/) for how detection works, confidence levels, and what to do when a service isn't found.

### Stale Hosts

Hosts discovery hasn't seen within their site's window carry a <StaleTag /> badge, and the host list has a **Stale only** filter to isolate them. This flags devices that may have gone offline without deleting them. See [Staleness](/using-scanopy/staleness/) for how the window works and why an entity goes stale.

### Hiding Hosts

Mark hosts as hidden to flag them for exclusion from the topology. Hidden hosts remain in the database with all their services, interfaces, and discovery history intact.

To toggle visibility:

1. Go to **Assets > Hosts**
2. Click the **Hide** button (eye icon) in the host's row

The button turns blue when a host is hidden. Use the **Hidden** column filter to find hidden hosts.

**When to use:**

- Flag decommissioned devices that shouldn't appear in diagrams
- Mark infrastructure hosts that clutter the visualization (PDUs, UPS units, management interfaces)
- Identify test or development hosts to exclude from production views

## Subnets

Subnets represent network segments. Scanopy automatically detects subnets during discovery, but you can also create them manually. Assign a type (LAN, WiFi, DMZ, etc.) to label your subnets for filtering and organization.

Like hosts and services, subnets can go [stale](/using-scanopy/staleness/) — carrying a <StaleTag /> badge and a **Stale only** filter when discovery hasn't seen them within their site's window.

### Utilization

The **Utilization** column shows how many of a subnet's usable addresses hold a discovered IP, as `used / usable` with a bar. The bar turns amber at 80% and red at 95%. Sort by the column to find the fullest subnets.

Usable addresses for IPv4 exclude the network and broadcast addresses, except on a `/31` (2 usable) and a `/32` (1 usable). An address held by more than one host, such as a shared virtual IP, counts once.

Select a subnet in the topology and the inspector's **Contents** box shows the same figure under **Utilization**.

### Nested ranges

A subnet that sits inside a larger one on the same site is nested in it. Recording `10.0.0.0/16` for a building whose VLANs are discovered as `/24`s nests each `/24` in the `/16`. A range's utilization counts the addresses in every subnet nested inside it as well as its own.

The subnet list opens grouped by CIDR, which shows each top-level range with everything inside it. The group is named after the top-level range and lists that range first. A range inside it that holds further ranges heads a collapsible section of its own, and a line down the left edge of each section joins the rows inside it. Subnets that nest with nothing fall in **Ungrouped**. To list subnets ungrouped, open the **CIDR** column's menu and choose **Clear grouping**.

In the topology inspector, a subnet's **This Subnet** box labels both ends of the nesting:

- **Within &lt;cidr&gt;** on a subnet, naming the most specific range that contains it.
- **Contains &lt;count&gt;** on a range, counting the subnets directly inside it.

Nesting ignores the [organizational subnets](#organizational-subnets) and container bridge networks, which belong to a single host. A range marked **Range assumed** shows no nesting label. Use **Resolve assumed range** on it to confirm the range, correct it, or merge it into a range that contains it.

### Organizational Subnets

Two special subnet types use CIDR `0.0.0.0/0` and serve as organizational containers rather than real network segments:

**Internet** — For public/external services:

- Public DNS servers (1.1.1.1, 8.8.8.8)
- Cloud services your network connects to
- External APIs

**Remote** — For hosts not on your local network:

- Mobile devices connecting via VPN
- Remote office machines
- Friend's servers you want to track
