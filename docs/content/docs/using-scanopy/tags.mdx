title: Tags
description: Organization-wide labels for categorizing and filtering entities, exclusive sets that hold one tag per entity, and the Application set that drives the Application perspective.
---

Tags are organization-wide labels you apply to hosts, services, subnets, sites, groups, and daemons. They're defined once for the organization, shared by every user, and usable across all sites. Deleting one removes it from every entity that carried it.

## Standard tags

Free-form labels. An entity can carry as many as you like, and they're used for filtering: in entity lists, and in the topology, where filtered elements fade rather than disappear so the layout stays stable.

Common schemes:

- **Criticality**: critical, high, medium, low
- **Ownership**: which team runs it
- **Compliance**: pci-scope, hipaa, gdpr, internal-only

Combining two axes is usually more useful than one long list. `production` + `critical` identifies core infrastructure in a way that neither tag does alone.

## Exclusive sets hold one tag per entity

A tag can belong to one exclusive set, and an entity holds at most one tag from each set:

- Adding a tag from a set replaces the tag from that set the entity already holds.
- Moving a tag into a set is refused while any entity holds two tags of that set. The error names how many entities to fix first.

Use a set for any scheme where each entity has exactly one value. Two examples:

| Set         | Tags                             |
| ----------- | -------------------------------- |
| Lifecycle   | Planned, Active, Decommissioned  |
| Environment | Production, Staging, Development |

With these sets, tagging a host **Decommissioned** removes its **Active** tag, and a host can't be both **Production** and **Staging**. Filter the host list by a tag to see every host in that state.

A set exists while at least one tag belongs to it.

## Application tags

**Application** is a built-in exclusive set. An application tag answers "what is this part of?" rather than "what is this like":

- A host or service carries **at most one**, as with any exclusive set.
- A service **inherits its host's** application tag. A host tagged `billing` lends that to every service on it, without tagging each one.
- Tagging a service directly **overrides** what it inherited. Use this for the service on a shared host that belongs to something else.

This inheritance is what the [Application perspective](/using-scanopy/topology/application/) groups on. Each application tag becomes a container, and services fall into it by their own tag or their host's. A host running one thing needs a single tag; only the exceptions need tagging individually.

## Icons

A tag can carry an icon from the [Lucide](https://lucide.dev/icons/) set. The icon shows on the tag in entity lists, tag pickers, and the topology tag filter. Application tags always use the application icon.

## Managing tags

Tags live under **Platform > Tags**, and can also be created inline while editing any entity. Renaming one updates it everywhere it's applied.

The **Exclusive set** field on a tag picks its set: **Application**, an existing set, or a new one. To start a new set, type its name and choose **Create "&lt;name&gt;"**. Leave the field empty for a standard tag.
