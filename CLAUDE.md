# Working in this repo

The marketing site (SvelteKit, `src/`) and the docs sub-site (Next.js + Fumadocs, `docs/`) build
together: `npm run build` builds both and copies the docs into `build/docs`. Deploys on push to
`main`.

Most of this file is about the docs, because that's where the expensive mistakes are. Every rule
below is paired with the drift it prevents — a rule without its reason gets optimized away by
the next person who finds it inconvenient.

---

## Documentation

### Generate, don't maintain

**Anything enumerable that exists in the Scanopy codebase gets rendered from a fixture. Never
typed into prose.** This is the single most important rule here, because every hand-maintained
list in these docs had already drifted before anyone noticed:

- The roles table offered a **Visualizer** role. There is no such role.
- The topology grouping table named a rule **Docker Stack**. The app calls it **Stack**.
- The Docker guide documented proxy port **2376**. The default is **2375**.
- Credential names were composed as `{integration} {transport}`, which produced **"UniFi
  Controller API Key"** — a credential type that does not exist. The app calls it **"UniFi API
  Key"**.

Fixtures live in `src/lib/fixtures/`. They are generated by scanopy's
`backend/src/server/shared/fixtures.rs` and copied here at release by
`.github/workflows/promote_to_latest.yml`.

- **Never hand-edit a fixture.** The next release overwrites it.
- Scanopy generates ~23 fixtures; only some are synced. Using a new one means adding a `cp`
  line to that workflow — the sync list, not the generator, is the bottleneck.
- Fixture types and lookups: `docs/src/lib/integrations.ts`.

Components that render them (`docs/src/components/`, registered in `docs/src/mdx-components.tsx`):

| Component                                                                                   | Renders                                                         |
| ------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `<DiscoverySources />`                                                                      | Every integration grouped by category, with what each discovers |
| `<IntegrationGuideLinks />`                                                                 | Inline links to every integration guide                         |
| `<IntegrationTransports id="…" />`                                                          | An integration's credential types, targets, daemon floor        |
| `<IntegrationFields id="…" transport="…" />`                                                | A credential type's fields, defaults, help text                 |
| `<IntegrationBeta id="…" />`                                                                | Beta notice — renders only if a transport is Beta               |
| `<CredentialBasics id="…" />`                                                               | The shared "credentials work the same everywhere" block         |
| `<CredentialTypesTable />`                                                                  | Every credential type across every integration                  |
| `<RolesTable />`, `<ElementRulesTable />`, `<ScanSettingsTable />`, `<DaemonConfigTable />` | Roles, topology grouping rules, scan settings, daemon config    |

Two consequences worth stating outright:

- **Beta status comes from the fixture's `stability` field, never from prose.** A hardcoded beta
  notice outlives the beta.
- **Guide URLs resolve from each guide's `integration` frontmatter** via `source.getPages()`.
  There is no link table to maintain, and a guide missing that field renders as plain text
  rather than linking somewhere wrong.

Known gap: `using-scanopy/network-data.mdx` still hardcodes the virtualization list
(Proxmox / vCenter / Docker / Podman) because scanopy has no fixture for it yet.

### One fact, one home

State a fact on the page that owns it. Everywhere else links.

What was found: the credential resolution order written out in full on **three** pages, SNMP
content spread across **four**, and the per-platform log commands duplicated between
`reference/daemon-configuration.mdx` and `setting-up-daemons/troubleshooting-setup.mdx`.

- **`reference/limitations.mdx` is for boundaries that decide whether Scanopy fits a
  situation** — IPv6, subnet size caps, Layer 2 vs Layer 3. Not per-feature caveats. Those
  belong with the feature, where a remedy can sit next to them.
- **A reference page documents what _is_ configured there.** Never "there is no setting to
  configure X" — `daemon-configuration.mdx` had three of these.
- The FAQ's short-answer-then-link shape is correct, not duplication.

### Write for the reader, not about the implementation

- **No UI mechanics.** Not which tabs a modal has, not which row lacks a remove button.
- **No internal process narration.** "The target IP is then cleared" describes our code, not
  anything the reader observes.
- **No design rationale.** State the fact. Keep the "why" only when it changes what the reader
  _does_ — "set the window above your scan interval" earns its place; "which is why the tag is
  amber, not red" does not.
- **Evergreen.** Describe the current state, never the transition from a previous one. "The tab
  lists keys but no longer creates them" only parses if you remember that it once did. Same for
  "predates version reporting" and "once a support floor is enforced".
- **Don't define behavior by contrast with a design that doesn't exist.** "The daemon that last
  discovered the host — evidence it can reach the address, rather than a guess from subnet
  membership" describes a road not taken; the reader never imagined the alternative and now has
  to. Same shape: "enforced by the server, not by convention", "targeted retries rather than
  simple broadcast flooding". Contrasting two things the reader can actually observe is fine —
  "the run completes rather than failing", "one cable rather than two".
- **Don't explain one integration by reference to another.** A reader on the UniFi page is there
  for UniFi. If a distinction between integrations needs explaining, it belongs in
  `using-scanopy/credentials.mdx`.

### Integration guides share an enforced skeleton

`docs/scripts/check-integration-guides.mjs` runs in `prebuild`, so a guide that drifts fails the
build. Each guide declares `integration: <fixture id>` in frontmatter and carries exactly:

```
What gets discovered → Prerequisites → Choosing a credential type
→ one section per transport, named by the fixture's display_name, in fixture order
→ Verifying it works → Troubleshooting
```

The checker also requires an `<IntegrationFields>` for **every** transport in the fixture, so a
credential type added upstream cannot ship undocumented.

Integration-specific troubleshooting lives in the guide's Troubleshooting section.
`setting-up-daemons/troubleshooting-scans/` is cross-integration only (host discovery, scan
performance, credentials).

### Structure and prose

- **Diátaxis placement**: how-to → `guides/`, concept → `using-scanopy/`, facts → `reference/`.
- A page that outgrows itself becomes a folder with a `meta.json` and subpages. `topology/` and
  `discovery/` are the examples.
- **A parallel list written as consecutive bold-label paragraphs should be a list or a table.**
  Exception: the `Symptoms` / `Cause` / `How to resolve` convention on troubleshooting pages and
  `daemon-status.mdx` is deliberate and consistent — leave it.
- **Measure prose per page, not per uninterrupted run.** A page that alternates paragraph and
  list scores clean on a longest-run metric while being dense throughout. That is exactly how
  `credentials.mdx` was missed.

### Claims we don't make

- **No first-hand testing claims.** Comparison pages and integration docs draw on public
  documentation and community reports.
- **No unverifiable security claims** — "encrypted at rest" and similar.

### Deleting or moving a page

Add both slash forms to `static/_redirects` as 301s:

```
/docs/old/path  /docs/new/path/  301
/docs/old/path/ /docs/new/path/  301
```

Also re-point any existing redirect that targeted the page you deleted — three rules were left
aiming at a page removed this session. **Anchors cannot be redirected**, so inbound links to a
section that moved to a subpage must be repointed by hand.

## Verifying docs changes

```sh
cd docs && npm run build        # prebuild runs the integration-guide checker
npx prettier --check docs/content/docs docs/src
git checkout -- docs/openapi.json docs/openapi-processed.json
```

That last line matters: `prebuild` rewrites both files on every run and they are not meant to be
committed — a previous commit exists purely to undo that churn.

Then check every internal link and anchor against the built output. There is no built-in
checker; this catches what the build won't:

```sh
cd docs && python3 - <<'EOF'
import re, glob, os
routes, anchors = set(), {}
for f in glob.glob('out/**/index.html', recursive=True):
    r = '/' + os.path.relpath(os.path.dirname(f), 'out')
    r = '/' if r == '/.' else r.rstrip('/')
    routes.add(r)
    anchors[r] = set(re.findall(r'<h[1-6][^>]*\sid="([^"]+)"', open(f).read()))
known = {'/troubleshooting', '/changelog'}   # pre-existing, not yours
bad = []
for f in glob.glob('content/docs/**/*.mdx', recursive=True):
    for link in re.findall(r'\]\((/[^)\s]*)\)', open(f).read()):
        if link in known: continue
        p, _, frag = link.partition('#'); p = p.rstrip('/') or '/'
        if p not in routes: bad.append((f, link, 'no page'))
        elif frag and frag not in anchors.get(p, set()): bad.append((f, link, 'no anchor'))
print(*bad, sep='\n') if bad else print(f'{len(routes)} routes, links OK')
EOF
```

If the build fails with `Export docs doesn't exist` pointing at `docs/src/lib/source.ts`, the
generated `.source/` directory is stale rather than the source being broken. `npx fumadocs-mdx`
regenerates it.

## Working conventions

- **Small changes go straight to `main`.** No feature branches, no PRs.
- **No AI attribution in commit messages** — no `Co-Authored-By` for assistants.
- **Nothing is urgent.** Docs and fixtures reach users only when Maya cuts a release, so an
  uncommitted change or a fixture that will be regenerated is fine sitting as it is. Report
  state plainly and let her sequence it.
- **Don't touch the `scanopy` repo** (`~/dev/scanopy`) unless asked. Docs changes that need a
  new fixture require a change there — propose it rather than making it.
